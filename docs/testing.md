# Testing

Cove is tested in layers. Each row of the release checklist is decided by the cheapest layer that can catch a regression in it, and a release only sends an agent or a person to the rows that nothing cheaper covers. The manifest that records this is described in [qa/README.md](../qa/README.md).

## Layers

| Layer | What it covers | How to run it |
| --- | --- | --- |
| Rust tests | Core behavior shared by both apps: wallets, send flow, labels, KeyTeleport, cloud backup, diagnostics, node and explorer settings, and the hardware-signer QR loop | `just test` |
| TAPSIGNER emulator tests | Cove's TAPSIGNER setup, PIN, derive, import and signing logic against Coinkite's card emulator | `just test-tapsigner-emulator` |
| iOS UI tests | Full-launch flows in the simulator | `just ios-ui-background` runs `CoveUITests/OnboardingFullLaunchUITests` by default; CI runs every class or method in the workflow's `IOS_UI_SUITES`. Pass other classes or methods, comma-separated, as the second argument, as in `just ios-ui-background "iPhone 17" CoveUITests/<Class>,CoveUITests/<Class>/<method>`. Classes that need scripted cloud storage and passkeys run in the Cloud Backup host app: name them under `CoveCloudBackupUITests/<Class>` and the scheme of that name is picked for you. `just ios-ui-foreground` shows the simulator |
| Android instrumented tests | Compose screens and full-launch flows on an emulator | `just android-instrumented-ci`, or `just android-instrumented-ci UiTest <package>.<Class>#<method>` for some tests in one flavour; staged process-death tests need `just android-ui-manual` |
| Device scripts | Navigate-and-observe checks on a real phone, with JSON results per row | `python3 -I qa/device/run.py android --serial <serial> --package org.bitcoinppl.cove.dev` or `python3 -I qa/device/run.py ios --bundle-id org.bitcoinppl.cove`; see [qa/device/README.md](../qa/device/README.md) for setup, `--list` and running a subset of rows |
| Agent pass | Checklist rows that need judgment, fixtures or multi-app flows, run by a coding agent driving a real phone | This document |
| Person | Camera, NFC, biometrics, haptics, spoken screen-reader output, hardware signers beyond the [hardware signing UI tests](#hardware-signing-ui-tests) | Batched into one sitting at the end |

UI tests that need a funded wallet get it from the fake Esplora and Electrum node in [`rust/crates/cove-fake-node`](../rust/crates/cove-fake-node/README.md), so they need no Signet funds or network. `just ios-ui-background`, `just ios-ui-foreground`, `just android-ui-manual` and `just android-instrumented-ci` start it for the length of the run, together with the hardware signer host (see [Hardware signing UI tests](#hardware-signing-ui-tests)). Each run takes its own block of host ports: the node's control API, Esplora and Electrum at the block's base and the two ports after it, and the signer host at base + 10 and base + 11. A run reserves the first free block from 39100 in steps of 100 with a lock in `/tmp/cove-ui-ports-<base>.lock`, held until its services stop, so several iOS and Android runs can share one machine, each with its own node. Runs from revisions before port blocks use 39000-39011 under `/tmp/cove-ui-tests.lock`, so no run takes that block. Android devices always see 39000-39002 and 39010-39011, which `adb reverse` maps to the run's block. iOS simulators share the host's loopback, so xtask passes the run's base to the iOS tests in `COVE_UI_TEST_PORT_BASE`. A run locks the Android device it uses, and an iOS run locks its worktree's UI test build, so a second run on either fails at once instead of replacing the first one's app or build. `emulator-5554` takes `/tmp/cove-android-emulator.lock`, the lock scripts and earlier revisions take for it, and a lock that a parent process holds, as a `lockf` wrapper does, counts as the run's own. Android runs only use emulators, never a physical phone: `ANDROID_SERIAL` must name an `emulator-*` device, or with it unset the run takes the only connected emulator. A run refuses an `ANDROID_SERIAL` that names a physical device, and with several emulators connected it refuses to start until `ANDROID_SERIAL` picks one, since tests on two emulators would reset and fund the same node. `just android-ui-manual` and the staged process-death tests also run every `adb` and Gradle call against that emulator. `just fake-node-run` and `cargo xtask ui-test-host run` without `--android` forward to such an emulator if one is connected, and leave physical devices alone. If xtask gets SIGINT, SIGTERM or SIGHUP during a run, it deletes the iOS simulators it made, removes its port forwards, and stops the fake node, the card emulator and every command it started, such as `xcodebuild` or Gradle, before exiting. A command still running 5 seconds after SIGTERM gets SIGKILL. A run that is itself killed before it finishes, such as by a supervisor's SIGKILL while CoreSimulator is slow, can leave its `Cove UI Test (pid N)` simulators behind; the next iOS UI run deletes those whose pid no longer runs. To run another command with the node up, use `just fake-node-run <command>` or `cargo xtask fake-node run -- <command>` from `rust/`.

`just android-ci-emulator`, or `cargo xtask android-ci-emulator --port <port>` from `rust/`, starts a headless emulator like the one the `UI tests` workflow runs the Android tests on: Android 15 (API 35) `google_apis` with the `pixel_6` profile, 4 cores, 4 GB, the workflow's emulator options and animations off. The only difference is the ABI, which follows this machine's, so Apple silicon gets arm64. On first use the recipe installs the system image, which needs the Android command-line tools in `$ANDROID_HOME/cmdline-tools/latest`, and creates the `CoveCI35` AVD. The emulator boots read-only, so several can run from the one AVD: `just android-ci-emulator 5556` starts a second on `emulator-5556`, and `ANDROID_SERIAL=emulator-5556 just android-instrumented-ci` runs tests on it while another run uses `emulator-5554`. A start that fails, times out or is interrupted before the emulator has booted stops the emulator again.

The CI workflow runs the TAPSIGNER emulator tests in their own job. The `UI tests` workflow runs the iOS UI tests and Android instrumented tests nightly and on pushes to master. On pull requests labeled `ui-tests` it runs only the Android tests, when the change reaches Android. It never runs the iOS UI tests on a pull request, because the three shards would hold most of GitHub's five concurrent macOS runners for up to two hours, so check a pull request's iOS UI tests locally or with a manual run. It splits the iOS suites listed in its `IOS_UI_SUITES` across three macOS runners, `ios-ui (1/3)` through `ios-ui (3/3)`; add a new suite class to that list. Android runs one job per flavour.

GitHub runs at most five macOS jobs at once for the whole organization, so CI's three macOS jobs, `compile-ios`, `swift-lint` and `test (macos-latest)`, can wait in its queue for hours. A maintainer can run the same commands on their own Mac with `cove-local-ci`, which posts a commit status for each job on the commit it tested, with the context `cove-local-ci/compile-ios`, `cove-local-ci/swift-lint` or `cove-local-ci/test`, then reruns the commit's CI run. CI's `changes` job reads those statuses with [`.github/scripts/ci_local_results.py`](../.github/scripts/ci_local_results.py) and skips a macOS job whose newest status is a success posted by a login in the workflow's `TRUSTED` list, which branch protection counts as passed. The run's summary lists the jobs a local run stood in for. Only accounts with push access can post statuses, so a fork can't skip a job, and when the statuses can't be read every macOS job runs. The local run tests the pull request's head while CI tests its merge commit with master, the same gap CI's own results have once master moves, since branch protection doesn't require branches to be up to date. [`test_ci_local_results.py`](../.github/scripts/test_ci_local_results.py) checks which statuses count, and that statuses it can't read skip nothing.

CodeQL runs from [`.github/workflows/codeql.yml`](../.github/workflows/codeql.yml) rather than code scanning's default setup, which must stay off for its uploads to be accepted. Actions, Python and Rust are analyzed without a build on every pull request and push to master. Swift needs the app built, Rust library first, on a macOS runner, so it's analyzed nightly and from a manual run, `gh workflow run codeql.yml --ref <branch>`.

On a pull request, both workflows run only the jobs its changes can affect. Their `changes` job diffs the pull request's merge commit against the base branch and passes the changed paths to [`.github/scripts/ci_changes.py`](../.github/scripts/ci_changes.py), which maps each path to the jobs that read it. A change under `android/` alone skips the iOS jobs and the Rust tests, a change under `ios/` alone skips the Android jobs and the Rust jobs other than the tests, which read the Xcode project and the UI test sources, and a docs-only change skips every job. Changes under `rust/`, to the justfile or under `tools/release-seams/` reach both apps, so they run every iOS and Android job, the lint jobs included. A path the script doesn't name, any change under `.github/`, a push to master, a scheduled run, a manual run without `base` and a diff the job can't compute all run every job, and so does a failed `changes` job. A skipped job shows as skipped in the pull request's checks, and branch protection counts that as passed. A new top-level file or directory that no job reads runs every job until it's added to the script's list of paths that run nothing. [`test_ci_changes.py`](../.github/scripts/test_ci_changes.py) checks the main rules and every fallback against throwaway git repositories. CI's `changes` job runs it first, and when it fails, every job runs. The `qa-manifest` job type-checks every script in `.github/scripts` with `mypy --strict`; run `python3 -I -m unittest discover -s .github/scripts -p "test_*.py"` to test them locally.

Pull requests only start CI when they target master, so a stacked branch gets CI from a manual run. Without `base`, it runs every job:

```sh
gh workflow run ci.yml --ref <branch>
gh workflow run ci.yml --ref <branch> -f base=<parent-branch>
```

With `base`, the run skips the jobs that the branch's changes since it left `<parent-branch>` don't need, as a pull request against that branch would.

`xtask ios-ui`, which the `ios-ui-*` recipes and CI run, builds each UI test scheme once with `xcodebuild build-for-testing` and runs each test with `test-without-building` on a simulator of its own. It creates a golden simulator from the model and runtime of the `--device` simulator and boots it once, then clones it for each test and each retry. A clone starts with no app, app data, keychain items or privacy grants, as an erased simulator does, without the erase and the slow first boot after it. The `--device` simulator itself is left alone. The run deletes its simulators, named `Cove UI Test`, when it ends, and the next run deletes any that a stopped run left behind.

Android has no such isolation. The test orchestrator starts a fresh process for each test, but every test in a flavour shares the app's data, and CI runs them in order of fully qualified class name. A full-launch test usually wipes the data when it launches the app, but a test that hosts a screen directly does not. Tests that set up an app lock skip themselves when one is already there, so they never replace a lock a person relies on, which means a lock left behind by an earlier test silently skips them. So a test that sets a PIN, decoy PIN, wipe data PIN or biometric unlock calls `restoreNoAppLock()` from `@After`, which removes all of them, leaves decoy mode and fails the test if the lock survives. Before tapping a full-launch screen with UiAutomator, wait for the target to stop moving: the lock cover slides up over the screen, and a key found mid-slide sends the tap to its neighbour

To check a fix without rerunning every suite, start the workflow on the branch with only the failed tests:

```sh
gh workflow run ui-tests.yml --ref <branch> \
  -f ios_tests=<Target>/<Class>/<method> \
  -f android_tests=<package>.<Class>#<method>
```

Both inputs take comma-separated lists, and a class runs all its tests. A run that names tests for only one platform skips the other platform's jobs before they take a runner. An iOS entry must be `<Target>/<Class>`, with `<Target>` `CoveUITests` or `CoveCloudBackupUITests` and a class that target builds, optionally followed by one of its test methods without `()`; anything else, such as a bare target or a module-qualified class, fails the run instead of running tests unexpanded. The iOS shards split the listed tests as they split a full run, each Android entry runs in every flavour whose test sources hold its class, and jobs with nothing listed finish without running tests. A manual run with both inputs empty runs everything.

A manual run shows under Actions but not in a pull request's checks, so it confirms a fix without clearing a failed check. To clear one, use GitHub's "Re-run failed jobs" on the pull request's run, which reruns only the failed shard or flavour, or push the fix.

CI runs the manifest check behind `just qa-check` on pull requests, so the manifest stays consistent with the tests it names. Its workflow filters pull requests to those targeting master, so run `just qa-check` locally before pushing a checklist change on a stacked branch, or start CI on the branch as shown above.

## Hardware signer tests

These Rust tests run the PSBT signing loops that a release pass would otherwise leave to a person with a camera or a card.

- **QR signing round trip** (`rust/src/hardware_signing_tests.rs`). A watch-only wallet is imported from the public descriptor of a fixed BIP39 test mnemonic and funded offline. Cove's send code then builds and saves a two-input draft, which is exported as animated UR (`crypto-psbt`) and BBQr frames with Cove's encoders. A BDK signer for the same mnemonic reads those frames with the `foundation-ur`, `ciborium` and `bbqr` crates, signs the PSBT and re-encodes it with the same crates. The signed frames go through `QrScanner::scan` one at a time: out of order, with repeats, and for UR with a missing frame that fountain parts later fill in. The result goes through the draft lookup and `finalize_psbt` that the hardware send screen uses, and the finalized transaction must spend the drafted inputs and pay the drafted recipient, change and fee, with valid signatures. The error-path test covers a truncated BBQr set, a PSBT from an unrelated signer, a PSBT the same seed signed on mainnet, and a signature for a deleted draft. Both tests run in `just test`
- **TAPSIGNER against the card emulator** (`rust/src/tap_card/tap_signer_reader/emulator_tests.rs`). Each test starts its own factory-fresh emulated card and drives Cove's `TapSignerReader` through the `TapcardTransportProtocol` callback that the iOS and Android NFC layers implement. The tests cover setup with the default and an advanced chain code, the factory PIN being replaced, a wrong PIN during setup, derive, backup and signing followed by a successful retry, import of the card's account as a wallet whose addresses must match the card's own xpub, and signing and finalizing a saved draft. The emulator's certificate chain doesn't lead to Coinkite's factory root, so the tests skip only that check after asserting that `create_tap_signer_reader` rejects the card. The emulator implements neither the rate limit nor `wait`, so the auth-delay paths stay covered only by the mock-transport tests in `tap_signer_reader.rs`

`just test-tapsigner-emulator` runs the emulator tests. It finds `ecard.py` in the `coinkite-tap-proto` submodule of the pinned rust-cktap checkout, installs the emulator's Python dependencies with uv into `~/.cache/cove/tapsigner-emulator-venv`, and runs the tests under cargo-nextest with `COVE_TAPSIGNER_EMULATOR_PYTHON` and `COVE_TAPSIGNER_EMULATOR_SCRIPT` set. The run fails when its filter selects no emulator test, so a renamed module cannot pass without running them. `just test` and `cargo test` list these tests as ignored, and when they are run without the emulator they fail with a message naming the recipe.

## Planning a release pass

1. **Identify the artifact.** Record the version, build number and commit from Settings → About on each phone. Plan against that commit, not the local branch: a TestFlight or Play build can lag the branch it was cut from.
2. **List the rows.** `just qa-plan <last-tested-commit>...<release-commit>` lists the rows whose code changed and that no automated test decides, split into agent and human rows. Use `just qa-plan-all` for a full pass.
3. **Run the automated layers first.** Green CI and a device-script run on each phone remove rows from the agent's list.
4. **Hand the agent rows to an agent per phone.** One agent per device at a time; WebDriverAgent serves every client on one session, so two drivers interfere.
5. **Batch the human rows** into one sitting after the agents finish, with the fixtures ready.

## Fixtures

Use test networks only. Cove's default Signet node is MutinyNet, whose 30-second blocks make funding fast. Never use production seed material, and keep fixture secrets out of the repository.

Automated UI tests don't use these fixtures. They reset the fake node, fund the wallet they import through its control API (`POST /reset`, then `POST /fund-wallet` with a public test mnemonic such as abandon ×11 about), and point the app at a custom Esplora node at the run's Esplora port, base + 1, which Android reaches at `http://127.0.0.1:39001`. Debug builds also fetch fee rates from `COVE_FEE_URL` when it is set, and the tests point it at the fake node so a send never reaches mempool.space. On iOS a fresh install can't reach Settings before it has a wallet, so debug builds launched with `COVE_UI_TEST_ESPLORA_URL` select Signet and that Esplora node at startup. The fake node checks the inputs, scripts and signatures of every broadcast, so a send with a bad signature fails, but it doesn't check fees or other mempool policy. The [crate README](../rust/crates/cove-fake-node/README.md) documents the API. `UtxoLockFullLaunchUITests` and `UtxoLockFullLaunchTest` use this setup to lock and unlock UTXOs from coin control and transaction details, then check which outputs the app's broadcasts spent.

- **Two funded Signet wallets** (for example Main and Secondary) with several UTXOs, including one small output, and known history
- **A watch-only hardware wallet** backed by a software signer such as Signer Lab, so the PSBT loop runs without a camera: export the unsigned PSBT to a file, review and sign it with the signer's CLI, then import the signed file in Cove. For QR and file fixtures, `just sign-psbt <psbt>`, where `<psbt>` is base64 or an absolute path to a `.psbt` file, signs it with the test mnemonic in `$MNEMONIC` and writes the result as base64, hex, binary, BBQr and UR images
- **Public-key fixtures** (`xpub`, `ypub`, `zpub`, `upub`, `vpub`, descriptors). To check the first receive address, use a freshly generated key with no history: published test vectors have on-chain history, so the receive index has already advanced past `/0/0` by the time Receive opens
- **A LAN HTTP block explorer** on the test machine, so explorer templates can be checked against the request log
- **The previous release** for in-place upgrade tests. On Android, the GitHub release APK and a locally signed build share the upload key, but a Play install is signed with Google's key and only updates through Play. iOS upgrades need the previous build from the App Store, since TestFlight only lists builds of the current version
- **Approval for destructive rows** before the run: clean install, uninstall, Wipe Data PIN and cloud backup deletion each need a recovery path prepared first

## Hardware signing UI tests

`HardwareSigningFullLaunchUITests` (iOS) and `HardwareSigningFullLaunchTest` (Android, `androidTestUiTest`) sign sends from hardware wallets without a camera or a card. They cover:

- **Animated QR signing:** a watch-only wallet imported from a scanned export sends Max, opens the unsigned PSBT's UR or BBQr export and takes the PSBT from its Copy button (the tests don't decode the displayed QR), imports the signature as animated frames fed in reverse order, checks the confirm screen and Advanced Details, and broadcasts to the fake node
- **Partial frames:** two BBQr frames show `Scanned 2 of N` and the parts left, a repeated frame doesn't count twice, and the rest complete the scan
- **Signatures that match no draft:** a signature for a deleted draft, one for an unrelated transaction and a mainnet one each show No Unsigned Transaction Found. On Android, a pasted signature for the deleted draft shows a Paste Error saying the transaction isn't pending. iOS doesn't test paste: under XCUITest the app reads an empty pasteboard, even after the host sets it with `simctl pbcopy`, and no paste prompt shows. Nothing checks a PSBT's network, so a mainnet signature is reported as an unknown transaction
- **TAPSIGNER:** import and signing through an emulated card, each with a wrong CVC and then a session that drops partway through before the retry succeeds. Until [#965](https://github.com/bitcoinppl/cove/issues/965) is fixed, rust-cktap rejects every BIP84 PSBT before it contacts the card, so the wrong CVC ends in the generic signing failure instead of Wrong PIN. Every signing error shows the same message, so in UI test builds the app also exposes the underlying one: iOS adds it to the Signing Failed! alert when the TAPSIGNER bridge is configured, and Android records it in its debug-only `UiTestSeams`. When the error is #965's Invalid path, the signing test stops there, as an expected failure on iOS and a skipped test on Android. Any other signing error fails the test, and Wrong PIN runs the whole flow

Two more suites use the same seams. `PublicKeyImportFullLaunchUITests` and `PublicKeyImportFullLaunchTest` import a hardware wallet from its bare public key, a vpub in a plain QR and a upub in a single-part BBQr, and the same keys from an NFC tag's text record, the vpub from onboarding's NFC scan and the upub from Add Wallet's, and check that Receive shows the first address and path of the address type the key names. The signer host derives the expected address from the mnemonic's key at `/0/0`, not from a descriptor. `TapSignerLayoutFullLaunchUITests` and `TapSignerLayoutFullLaunchTest` set up a factory-fresh emulated card and then import a set-up one at the largest text size (the `AccessibilityXXXL` content size on iOS, a system font scale of 2 on Android), dropping a session in each so the retry screens show. On the choose, advanced, PIN, retry and success screens they scroll each title and action into view and fail if it never fits inside the window, if an action is disabled or takes no tap, or, on Android, if it is squeezed. They also fail when a title, description or action label draws truncated in place, which neither platform's UI tree shows, since both report a label's whole text. Android reads the layout of every text in the TAPSIGNER sheet from Compose and fails if a line is ellipsized or the text needs more lines, height or width than it gets. iOS titles, descriptions and button labels carry the truncation probe below. Signing asks for the CVC with its own message, and no test opens that screen at the largest text size, so its layout still needs a person

iOS has one more. `WatchOnlyUpgradeFullLaunchUITests` imports the same watch-only export, scans a BIP329 label for its funding transaction from the wallet's QR scanner, then enters the test mnemonic from Add Wallet. The wallet it lands on must be the same one, still listed once under its imported name with its balance and label, and now offering View Secret Words in its settings

### Test seams

Debug builds have four seams the tests drive. Each is off unless its environment variable is set, and none is in release builds: iOS compiles them under `#if DEBUG`, which only the Debug configuration defines, Android keeps them in `src/debug`, with inert stubs in `src/release`, and the Rust part is under `cfg(debug_assertions)`, which no release profile enables. `cargo xtask check-release-seams` (from `rust/`; `--ios`, `--android` or `--rust` for one layer) builds the release Swift code, the shrunk release dex and the `release-speed` Rust library, and fails if a seam's environment variable name or the emulator's root key is in any of them, with a debug build of each as the control that the check would find them. Xcode and Gradle package whichever Rust library was built last, so device Release builds and archives in Xcode, and every Gradle release variant, also run `tools/release-seams/check-packaged-rust.sh` on the library they are about to package and fail if it has a seam, as a debug Rust build does. Rebuild Rust with `just build-ios-release` or `just build-android-release` first. The check's markers are in `tools/release-seams/rust-markers.txt`, which `check-release-seams` reads too.

- **QR scanner** (`COVE_UI_TEST_QR_SCRIPT`): set to a file path. While a scanner is open it takes the file, deletes it, and scans each string of its `{"frames": [...]}` 150 ms apart through the same code the camera feeds, so progress, haptics, errors and completion behave as with a camera. Write the file atomically, since the scanner polls for it. iOS tests use a path under `/tmp`, which the simulator shares with the host, and pass it in the launch environment. Android tests use the app's `noBackupFilesDir` and set the variable in process with `Os.setenv`, which the app reads when a scanner opens
- **TAPSIGNER transport** (`COVE_UI_TEST_TAPSIGNER_BRIDGE`): set to `host:port`. TAPSIGNER commands, and the NFC tag read that finds the card, go over TCP to that address instead of an NFC session, each APDU as a frame with a 4-byte big-endian length. The app's TAPSIGNER code above the transport is unchanged, except that Cove, which accepts only cards whose certificates chain to Coinkite's factory root, also accepts the emulator's root while the variable is set. The emulator's root private key is public, which is why that trust is compiled into debug builds only
- **Text truncation probe** (`COVE_UI_TEST_TRUNCATION_PROBE`, iOS only): set to `1`. Each probed text, such as the TAPSIGNER screen titles, descriptions and button labels, lays out a hidden copy of itself with no line limit at the width it draws at and sets its accessibility value to `fits`, or to `truncated` when the copy is taller. It reports `offscreen` instead when the text's frame in the window runs past either side of the window, which XCUITest can't see because UIKit clips an element's accessibility frame to its list cell. A test reads the value from the text's `value`, or from its button's, which takes its label's value. `ProbedLabel` is a `Label` whose title carries the probe. A view that merges its texts into one accessibility element, such as a Cloud Backup wallet row or the Restore All progress, never shows their values, so `uiTestTruncationReport(identifier)` lays an invisible element with that identifier behind it, where it takes none of the view's taps, whose value is `fits` when the view holds a probed text and every one of them draws whole, and `truncated` when any of them is truncated or offscreen. Without the variable, and in release builds, the probe leaves the text unchanged and the report adds nothing
- **NFC tags** (`COVE_UI_TEST_NFC_NDEF_SCRIPT`): set to a file path. While an NFC scan is active it takes the file, deletes it, and reads the hex in its `{"ndef": "…"}` as the raw NDEF message a tag holds, parsed by the platform (`NdefMessage` on Android, `NFCNDEFMessage` on iOS) and processed by the same code an NDEF tag read uses, so only the NFC session is replaced. iOS reads ISO 15693 tags block by block and parses them in Rust instead, a path the seam doesn't reach. Write the file atomically, and pass the path as for the QR scanner. The TAPSIGNER transport takes precedence when both are set

The Android `UiTest` flavour, which only test builds use, replaces the cloud provider, the passkey provider and the network monitor with scripted ones. A test can drop and restore the network with `ScriptedConnectivityAccess.setConnected`: the change reaches Rust the way the real network monitor reports it, and while the network is down the scripted provider fails every request as offline, as Google Drive does. The emulator's own network stays up for the fake node and the signer host. After a restore from the fixture backup, the scripted provider keeps the wallet backups Cove uploads, including those of wallets added on the device, and serves them back, so Cove can confirm its own uploads. A test can also reject the next upload of an added wallet as over quota, which Cove does not retry on its own, to leave a wallet waiting for Sync Now.

### Host services

`cargo xtask ui-test-host run [--android] -- <command>` runs the command with the fake node and the hardware signer host up, forwarding all their ports to an emulator with `--android`, as `just android-instrumented-ci` does, and failing when none is connected. The command runs with `ANDROID_SERIAL` set to the emulator the ports went to. The xtask iOS and Android UI test runners start it themselves. The signer host serves:

- **Control API on base + 10, 39010 on Android:** `POST /sign-psbt` signs a PSBT with a mnemonic as a hardware wallet would and returns it as base64 and as UR and BBQr frames, `/unrelated-psbt` signs one that matches no draft, `/watch-only-descriptor` returns the account a hardware wallet exports, `/public-key-export` returns an account's bare vpub or upub as a plain QR and a single-part BBQr with the first receive address it should import as, `/simulator-pasteboard` reads an iOS simulator's pasteboard, so iOS tests read a copied PSBT without the paste prompt, `/simulator-appearance` switches the simulator between light and dark mode, and `/simulator-content-size` answers with the simulator's text size and, given a `content_size`, then sets it with `simctl ui content_size`, failing instead when simctl reports no size. `/tapsigner/start` starts a fresh emulated TAPSIGNER with CVC 123456, set up with a key or, with `{"needs_setup": true}`, factory fresh, and `/tapsigner/drop` ends its next session after a number of exchanges, as a card pulled from the field would. The `/keyteleport/...` routes play the other phone in a KeyTeleport transfer, described below
- **TAPSIGNER bridge on base + 11, 39011 on Android:** passes APDUs to Coinkite's `ecard.py` emulator from the rust-cktap checkout `Cargo.lock` pins. The host prepares the emulator when it starts, before any test asks for a card, so a first-time setup doesn't count against a test's request timeout. The emulator runs in the same uv venv `just test-tapsigner-emulator` uses, `~/.cache/cove/tapsigner-emulator-venv`, or in the Python `COVE_ECARD_PYTHON` names. If the host can't prepare the emulator, for example because uv is missing, it prints a warning, and only the TAPSIGNER tests fail. The emulator writes its output to `rust/target/ui-test-host/ecard-<base>.log`, such as `ecard-39100.log`,, which a failed `UI tests` job uploads as a `tapsigner-emulator-log-*` artifact. When a card fails to start, the `/tapsigner/start` error, and so the test's failure message, ends with the last lines of that log. The host logs how long each card took to listen. A card that doesn't listen within 45 seconds gets a SIGABRT first, so the log shows where each Python thread was stuck

To run the tests alone:

```sh
just ios-ui-background "iPhone 17" CoveUITests/HardwareSigningFullLaunchUITests
cd android && ANDROID_SERIAL=<emulator-serial> cargo run -q --manifest-path ../rust/Cargo.toml -p xtask -- ui-test-host run --android -- ./gradlew connectedUiTestDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=org.bitcoinppl.cove.flows.SendFlow.HardwareSigningFullLaunchTest
```

Camera and NFC hardware themselves, and real signing devices, still need a person.

### Live text size

`ReceiveTextSizeFullLaunchUITests` (iOS) opens Receive at the largest and the default text size. `testReceiveControlsMatchAtLargestAndDefaultTextSize` sets the size per launch with the `-UIPreferredContentSizeCategoryName` launch argument, which pins it for that launch, so it never sees a size change while the app runs. `testReceiveLaysOutAgainWhenTextSizeChangesWhileOpen` sets the simulator's own size through `/simulator-content-size` instead: it launches at `accessibility-extra-extra-extra-large`, opens Receive and reads its address, then sets `large` while the app keeps running and Receive stays open, which the app gets as a live `UIContentSizeCategory.didChangeNotification`. It fails unless Copy Address shrinks to the default layout, Done, Copy Address and Create New Address are all usable, and the address is the one Receive showed at the largest size. Before the first change the test reads the simulator's size and registers a teardown block that puts it back, so it is restored even when the test fails or a change's answer never arrives. On Android the `s16-restore-normal-font-and-compare-receive-controls` device script changes `font_scale` while the app runs and reopens Receive, since a font scale change recreates the activity

### KeyTeleport tests

The `/keyteleport/...` routes let the host play the other phone in a KeyTeleport transfer, using the `keyteleport` crate the app uses. The app shows its receiver request and its sender response only as QR codes, so the iOS tests read them as a second phone's camera would, by decoding the QR code in a screenshot with Core Image, and read codes and passwords from the screen once revealed. In the screenshot under each hint they check that no QR code decodes and that Vision text recognition reads the hint and nothing beyond it, allowing two misread characters and the eye icon, before anything is revealed and after each switch, so revealing one conceals the other.

`KeyTeleportReceiveFullLaunchUITests` (iOS) receives with the host as the sending phone. `POST /keyteleport/send` encrypts a mnemonic or master xprv for the app's request, or COLDCARD Secure Notes the way COLDCARD firmware does, and returns the response as BBQr frames, several when `min_parts` asks for them or the payload is too big for one QR code, with its Teleport Password. The test shows the frames to the scanner through the QR seam and types the password. It covers the mnemonic and xprv reviews (reveal, hide, copy, Finish Without Importing and Import Wallet), a multi-part response scanned out of order, and every review and result screen at the largest text size in dark mode, which `/simulator-appearance` switches on. The two largest-text tests aren't in `IOS_UI_SUITES` or mapped to a checklist row until they pass on GitHub. XCUITest reports a truncated label in full, so those layout checks also read the screenshot with Vision, failing on an ellipsis below the status bar (whose clock and signal dots Vision reads as one line with content scrolled beneath them), or when Vision can't read the start and end of a text or button label where it is drawn. A text taller than 60% of its scroll area below the navigation bar, such as a revealed xprv at the largest size, is scrolled through instead, since a drag moves 40% and could step over the room it has to show whole: Vision must read its start once its first line shows and its end once its last line shows, with no ellipsis at either.

`KeyTeleportSendFullLaunchUITests` (iOS) turns this around: `/keyteleport/receive-request` makes a receiver request for the app to scan, the test sends the wallet's recovery words from Wallet Settings, entering the PIN they ask for, and `/keyteleport/receive-response` decrypts what the app showed back to the wallet's words. The camera itself still needs a person

`KeyTeleportAppScannerFullLaunchUITests` (iOS) and `KeyTeleportAppScannerFullLaunchTest` (Android) receive through the app-wide QR scanner instead of the receive screen's own: they show the request, leave the receive screen, and scan the host's multi-part response from Add Wallet's scanner on iOS or the wallet's on Android. The scan must reopen the stored receive at the Teleport Password and unlock to the review. The Android test scans the frames out of order with one repeated and checks the "Scanned i of N" progress on the way. On iOS the only other way in is Open With for a text or JSON file. The unit test `KeyTeleportFileOpenTests` hands the app's open-URL handler a text file holding a sender response, made in-process for a receive that was started and left, and checks that it reopens the stored receive at the Teleport Password. A second case opens a receiver request file and checks that it starts a send. Android builds ship the KeyTeleport link and share intent filters disabled, and `KeyTeleportLinksDisabledTest` checks that a keyteleport.com link and shared text still resolve to no Cove activity. One phone's camera reading the other's QR codes stays with the migration journeys

## Cloud Backup UI tests

Cloud Backup UI tests run the whole app against a scripted cloud provider and passkey provider, so they need no iCloud or Google account and no real passkey. Neither provider ships: on iOS they live in the `CoveCloudBackupUITestHost` app, which builds all of `ios/Cove` with its own entry point, and on Android in the `uiTest` flavour's `ScriptedCloudStorageAccess` and `ScriptedPasskeyProvider`.

### iOS host controls

A `CoveCloudBackupUITests` test that creates a `CloudBackupHostControl` scripts the host through a directory under `/tmp`, which the simulator shares with the Mac. The control passes the directory to the app in `COVE_CLOUD_BACKUP_UI_CONTROL_DIR`. The directory holds:

- **`script.json`:** a `CloudBackupUITestScript`, written atomically and read again on every provider call, so a test can change it while the app runs. It picks the fixture cloud (the generated backup in `CloudBackupFixture.json`) or a fresh-enable cloud that starts empty, and scripts namespace listings, which fixture wallets are listed, each wallet download's result, upload failures by attempt, a `masterDownloadFailure` that fails every master key download after a given number have been served, and each passkey create, assertion and discovery result. `answerNextPasskeyAssertions` scripts the next assertions from wherever the test is, for example a cancel and then a success
- **Wallets added on the device:** the fixture cloud keeps an upload of a wallet the fixture doesn't hold, then lists, reports and serves it like the fixture's own. The script's `newWalletUploadFailures` fails those uploads in order across launches, and `quotaExceeded` is the one upload error Cove doesn't retry, so a wallet it rejects waits for Sync Now. A rejected upload is reported missing, as Google Drive does on Android
- **Holds:** a scripted hold parks one provider call (a namespace listing, a wallet listing, a wallet download, a wallet upload before the cloud stores it, the return of a master key upload after the cloud stored it, a passkey registration or assertion before it answers, or the keychain delete of the pending enable journal that ends an enable's local promotion) until the test creates the matching `release-<id>` file. The host records each hold it enters in `state.json` and never enters it again, even after a relaunch. `holdWalletDownload` counts downloads from the moment it is called, since inventory refreshes also read each record, and `holdNextWalletUpload`, `holdNextWalletList` and `holdNextWalletListSnapshot` hold the next upload, full listing or detail inventory snapshot from whichever action makes it. Holds set together start from the same count, so concurrent listings each take one whichever reaches the host first
- **Delayed visibility:** the fresh-enable cloud accepts uploads but reports them pending, lists nothing and serves nothing until the test creates `release-visibility`, as a slow iCloud sync would
- **Network:** the script's `networkConnected` drops or restores the network. While it is down every provider call fails as offline, and the host's `ControlledConnectivityAccess`, which replaces the production network monitor, tells Rust the device is offline. The host reads the script again every 100 ms and records what it last told Rust in `state.json`, and `setNetworkConnected` waits for that, so a test knows Rust heard the change. The simulator's own network stays up for the fake node
- **`app-state.json`:** the cloud backup manager's state as the app holds it, a `CloudBackupUITestAppState` with the inventory state, whether its rows are ready and complete, the inventory error, the cloud-only rows, Restore All, the verification state and whether it waits for uploads to confirm, the Sync Now state and error, each on-device wallet's row with its sync status, the lifecycle, and the Settings row status the app would show, rewritten on every change. The Cloud Backup form builds only rows near the screen, so `waitForAppState` checks what the app holds while the test checks the screen
- **`state.json`:** the host's call counts per provider call, namespace deletions included, in total and per launch, the holds it entered, each upload with whether the cloud accepted it and whether it was a new wallet's, and the credential ids the app authenticated with, so a test can check that a retry created no second passkey or that a relaunch did no work on its own. A wallet download made with consent allowed is also counted as `consentWalletDownload.<recordId>`: restoring a cloud-only wallet reads it that way while startup reads a cloud-only record silently, so a relaunch test can count restore attempts from the launch itself. A call refused because the network is down counts as `offlineRejection` rather than as the call, so counts show only calls the provider served
- **`app.log`:** the app's stdout and stderr, Rust logs included, across launches. The simulator clone is deleted after each test, so a failed test attaches this log to its result
- **Persistence:** uploads land under `cloud/` and the keychain in `keychain.json`, so `CloudBackupHostRobot.killAndRelaunch` restarts the app on the same cloud and keychain. A test can edit the keychain between the two launches with `removeKeychainItems(containing:)`

`CloudBackupLargeTextFullAppUITests` runs the host at the largest accessibility text size with the truncation probe on. It reaches the setup description, the inventory with its on-device and cloud-only rows, a passed and a failed verification, the Restore All progress, the missing passkey screen and the incomplete-setup recovery screen. It gets the missing passkey screen from a passkey repair that the host holds at registration and then fails. It gets the recovery screen from an enable killed after its master key upload, whose staged key the test deletes from the keychain before relaunching. On each of those screens after the setup description it scrolls every text and action until it lies wholly below the navigation bar, then fails if a probe or report says `truncated` or `offscreen`, if an action takes no tap where it is drawn, or if an action that should be enabled is disabled. The setup description test, which came first, only checks that its acknowledgements and Enable can be scrolled to, tapped and enabled.

Without the variable the host keeps its fixed scenarios in `COVE_CLOUD_BACKUP_UI_SCENARIO`. The fixture's extra wallets come from the ignored generators in `rust/src/manager/cloud_backup_manager/ops/tests/ui_fixture.rs`, whose non-ignored tests check the pasted records.

### Android scripted providers

`ScriptedConnectivityAccess.setConnected` drops or restores the network the same way, and `ScriptedCloudStorageAccess` scripts the rest of the same cases in process: `configureFreshEnableWithDelayedVisibility` for a fresh enable whose uploads stay hidden until released, `configureProductionFixtureRestore` for the fixture cloud, blocks on namespace and wallet listings, wallet downloads and wallet uploads, `closeWalletListGate` to park every wallet listing until `releaseWalletListGate`, and `failUpload(kind, attempt)` to reject one master key or wallet upload, with `uploadCount` and `awaitUploadCount` to check retries. `exposeProductionFixtureWallets` lists any of the fixture's records, including the private-key wallet and the iOS fixture's second backup of Fixture Wallet One. `holdWalletDownload(recordId, matchingRequestsToSkip, policy)` parks one record's download until `releaseWalletDownloadHold`; unlike `blockNextWalletDownload`, holds on several records can be pending at once, and `heldWalletDownloadRecordIds` lists the ones parked now, so a test can see which wallet a batch reads and that it reads one at a time. Like `holdWalletDownload` on iOS, a hold counts downloads from the moment it is set, since inventory refreshes also read each record. With a `policy`, it counts only downloads made under that `CloudAccessPolicy`: Restore All reads with consent allowed, while a background cloud-only refetch reads the same records silently. Reads of a backup Cove uploaded during the test are served from that upload and never reach a hold. `consentWalletDownloadCount(recordId)` counts downloads made with consent allowed in the current process, the reads a restore attempt makes, as the iOS host's `consentWalletDownload` does. The fresh-enable cloud also counts upload confirmation checks of each record (`mostUploadStatusChecksOfOneRecord`) and namespace deletions (`namespaceDeleteCount`). `ScriptedPasskeyProvider` scripts and counts passkey calls, and its `creationHold` and `authenticationHold` park the next registration or assertion. The `uiTest` application wraps the real keychain in `HoldableKeychainAccess`, whose `pendingEnableJournalDelete` hold parks the delete that ends an enable's local promotion. A staged process test that ends while a hold is parked leaves the app inside that call until the runner force-stops it, which is how `cargo xtask android-ui-enable-interruption`, part of `just android-ui-manual`, kills a fresh enable during passkey registration, passkey confirmation and promotion; `--only registration`, `confirmation` or `promotion` runs one of them. A gate or block set before a staged stage launches the app catches that process's first calls, which is how `cargo xtask android-ui-first-inventory`, also part of `just android-ui-manual`, holds every listing a relaunched app makes, including bootstrap's inventory discovery and passkey verification, together with its first detail snapshot.

## Driving devices

### Android

[`tools/uia2`](../tools/uia2/README.md) drives a phone or emulator through the UiAutomator2 server. `android-vis` prints the visible elements with tap centers, `android-tap-label` taps by test tag or text, and `android-shot` takes a screenshot for visual checks.

- Screens that hold secrets set `FLAG_SECURE`, so screenshots and screen recordings of them come back blank. Never print or save the raw UI tree from `android-source` on those screens: it contains the secret values. For word-layout checks, keep word values in memory and record only indexes and bounds
- Restore any font scale, animation scale or airplane mode change at the end, as the device scripts do

### iOS

[`tools/wda`](../tools/wda/README.md) drives an iPhone through WebDriverAgent with `ios-*` commands that mirror the `android-*` ones: `ios-vis` to read the screen, `ios-tap-label` to tap, `ios-shot` for screenshots. iPhone Mirroring ignores synthetic scrolls and can't run while WDA is driving the phone, so use WDA for automation. The tools README covers the pasteboard, swipe holds, stalls and the other behavior to know.

- **System dialogs** such as Allow Paste and the share sheet aren't in Cove's tree. Tap them by coordinates from a screenshot
- **Stalls are findings:** when tree reads and taps time out while screenshots still work, Cove's main thread is blocked. Record it with a screenshot instead of retrying
- **Never take a screenshot of a recovery-word screen.** For word-layout checks, keep word values in memory and record only indexes and bounds

## Running an agent pass

Give the agent a brief with:

- **Scope:** the row ids from `just qa-plan`, the artifact under test and the devices
- **Hard rules:** test networks only, no mainnet sends without approval, no screenshots of recovery words, never print or save secrets, and no wipe, uninstall, cloud backup deletion or account sign-out without approval. Restore every phone and app setting the run changes, and record the final state
- **Fixtures:** wallet names, which signer to use, the explorer address and anything the brief assumes exists
- **Human hand-offs:** the rows the agent should mark HUMAN instead of attempting
- **Results format:** as below

Ask for a checklist file the agent updates as it goes, and a closing summary that lists what needs a person first.

## Recording results

Record one result per platform for each row, with evidence paths and a timestamped note:

- `PASS`: the whole row was exercised and held. If only part was exercised, it isn't a PASS
- `FAIL`: the app misbehaved. Record the exact input, the screen and the evidence. Check the same case on the other platform before marking it N/A there: much of Cove's behavior is shared Rust code
- `HUMAN`: needs a person, with the reason (camera, NFC, biometrics and so on)
- `BLOCKED`: the run couldn't reach the state the row needs. Name the missing fixture, instrument or approval, so the next run can supply it
- `N/A`: the row doesn't apply to that platform

Keep screenshots, UI trees and logs next to the results, and never include secrets in them.

## Rows that need a person

These still need hands and eyes:

- QR camera scans: PSBT UR and BBQr, SeedQR, one phone reading the other's KeyTeleport QR codes, watch-only import. The [hardware signer tests](#hardware-signer-tests) cover the PSBT frames and their import, and the [KeyTeleport tests](#keyteleport-tests) cover scanning and routing a response through the QR seam; the camera and a strict external signer still need a person
- NFC: TAPSIGNER setup and signing, reading a hardware wallet or tag, removing a card mid-operation. The emulator tests cover Cove's card logic and the NFC tag seam covers what the app does with a tag's NDEF records; an iOS import from an ISO 15693 tag, which skips NDEF, a physical card or tag, the NFC session and card removal still need a person
- Biometric success, and the strength of PIN keypad haptics
- Spoken VoiceOver and TalkBack output and natural focus order
- COLDCARD and other hardware signers
- Passkey creation and approval with a real account when enabling or restoring Cloud Backup
- Cloud Backup flows whose tests stop short of the production path, such as recovering an interrupted setup or a partly finished Restore All after a restart, the inventory refresh after reconnecting, verification and Sync Now on iOS, retrying a failed setup upload, and a restored wallet's history after its full scan. Rust tests with scripted passkey and cloud providers cover the cancel, retry, inventory and restore logic underneath, and each row's manifest comment says which part stays manual
- Signing in or out of iCloud or Google accounts

Some neighboring checks don't need a person. KeyTeleport transfers between two Cove phones run end to end through both Rust managers in `rust/src/manager/key_teleport_manager/tests/round_trip.rs`, and COLDCARD payloads (mnemonics, master keys, raw master secrets, notes, Seed Vault entries, backups and PSBTs) are encrypted the way COLDCARD firmware does in `tests/coldcard.rs`, so only the camera scan between devices needs a person. Cove's HTTP client trusts only its bundled webpki roots, not certificates installed on the phone, so an intercepting proxy can't read the diagnostics upload. The tests in `rust/src/diagnostics/upload.rs` send a report to a local collector through `COVE_DIAGNOSTICS_URL` and check the request as it arrives: the `application/age` content type, the key-id header, and an age-encrypted body that contains no report text. Debug builds send reports to `COVE_DIAGNOSTICS_URL` when it is set, so the same check works against a running app. The report is encrypted to the production key, so that collector can't read its contents.

## After a pass

- Give every FAIL a regression test at the cheapest layer that can catch it. Record it in the manifest under `pending` with its pull request, then under `coverage` once it merges
- Turn any agent steps that only navigate and observe into a device script in `qa/device`, so the next release runs them with a command
- Update fixtures and this document with anything the run had to work around
